# Antifraud system

Система для обнаружения мошеннических транзакций в реальном времени с использованием ML-модели, Kafka для потоковой обработки данных и Airflow для пайплайнов по расписанию.

## 🏗️ Архитектура

Компоненты системы:
1. **`interface`** (Streamlit UI):
   
   Представляет интерфейс для ручной симуляции потока данных (альтернатива transactions_simulator) в ML сервис и предоставляет возможность просмотра результатов скоринга.
    - Имитирует отправку транзакций в Kafka через CSV-файлы.
    - Загружает транзакции отдельными сообщениями формата JSON в топик kafka `transactions`
    - Предоставляет информацию о результатах предсказания для транзакций, сохраненных в БД PostgreSQL
    
2. **`fraud_detector`** (ML Service):
   - Загружает предобученную модель LightGBM
   - Выполняет препроцессинг данных:
     - Извлечение временных признаков
     - Гео-расстояния
     - Кодирование категориальных переменных
   - Производит скоринг с порогом 0.85.
   - Выгружает результат скоринга в топик kafka `scoring`

3. **`Kafka`**:
   - Zookeeper + Kafka брокер
   - kafka-setup: автоматически создает топики `transactions` и `scoring`
   - Kafka UI: веб-интерфейс для мониторинга сообщений (порт 8080)

4. **`database`**:
    - поднимается база данных PostgreSQL для хранения результатов скоринга по транзакциям
    - также содержит датасет размеченных транзакций для переобучения модели
    - writer: сервис для записи сообщений брокера в БД

5. **`data_loader`**:
   - загружает train.csv в поднятую докером базу данных 

6. **`transactions_simulator`**:
   - имитирует процесс появления новых транзакций для скоринга
   - каждые 0.25 секунд берет случайную строку из датасета и отправляет в топик transactions kafka

7. **`dags`**:

   Содержит пайплайны задач для работы сервиса:
    - `retrain_model`: 
      - выполняет процесс переобучения модели с использованием данных за новый месяц (используется 3 месяца, старый месяц стирается). 
      - если качество новой модели хуже ранее опубликованной по F1 score, то публикация новой модели не выполняется: ее веса сохраняются, но изменения в файле latest.txt (хранящий актуальную весрию модели) не происходит, вызывается SkipTaskException.

    - `supply_batch`: 
      - по расписанию дописывает в размеченную витрину новый месяц: берёт выборку уже лежащих строк, переносит transaction_time в следующий календарный месяц и добавляет батч размером 50000 строк в витрину
      - наблюдения старше 3 лет из истории удаляются

    - `check_data_quality`: 
      - после переобучения модели вызывается dag для проверки качества тренировочного датасета 
      - правила data quality: баланс классов, пропуски, диапазон amount, выбросы по amount, дубликаты, низкая изменчивость признаков
      - результаты оформляются в виде HTML отчета и сохраняются в reports/
      - в случае провала критичных проверок (в данных только 1 класс или amount в невалидном диапазоне) задача вызывает исключение

## Технологии

- **Python 3.11**
- **ML**: LightGBM, pandas, numpy
- **Kafka**: потоковая обработка данных
- **PostgreSQL**: витрина размеченных данных и результаты скоринга
- **Airflow 2.10**: поставка месячных батчей, переобучение модели и проверка качества данных
- **Docker / Docker Compose**: оркестрация микросервисов

## 🚀 Быстрый старт

### Требования
- Docker 28.2.2
- Docker Compose 2.36.2

### Запуск
```bash
git clone https://github.com/Timur-ingrzv/fraud-detector.git
cd fraud-detector

# Сборка и запуск всех сервисов
docker compose up -d --build
```
После запуска:
- **Streamlit UI**: http://localhost:8501
- **Kafka UI**: http://localhost:8080
- **Airflow**: http://localhost:8081
- **Логи сервисов**: 
  ```bash
  docker compose logs <service_name>  # Например: fraud_detector, kafka, interface
   ```

## Data Quality

Проверка качества тренировочных данных выполняется DAG'ом 
`check_data_quality` и запускается автоматически после переобучения модели.
Отчёт сохраняется в `reports/dq_report_<UTC-timestamp>.html`.

### Правила проверок

| Правило | Severity | Что проверяет | Порог |
|---|---|---|---|
| `target_balance` | CRITICAL | Доля положительного класса в `target` | `> DQ_RULES["target_balance_min"]` |
| `missing_values` | CRITICAL | Максимальная доля пропусков в любой колонке | `< DQ_RULES["missing_ratio_max"]` |
| `amount_range` | CRITICAL | Отсутствие отрицательных сумм транзакций | `0` негативных значений |
| `amount_outliers` | WARNING | Доля выбросов по `amount` (z-score) | `< DQ_RULES["amount_outlier_ratio_max"]` |
| `duplicates` | CRITICAL | Доля полных дублей строк | `< DQ_RULES["duplicate_ratio_max"]` |
| `constant_features` | WARNING | Константные признаки (std = eps) | `0` таких колонок |

Пороговые значения задаются в `pipeline/settings.py` в словаре `DQ_RULES`.

Для полной функциональности убедитесь, что:

3. Порты 8080, 8081, 8501, 9095, 5433 свободны на хосте
